## 📋 Resumen: Fix R3-missing-prisma-generate — `e2e:fresh` regenera el cliente Prisma SQLite antes del seed

Aterrizaje en `noche/serie-noche-2` del fix del hallazgo **CRITICAL
R3-missing-prisma-generate** del review RDD de la porción C3 (SERIE-NOCHE-2).
`scripts/e2e-fresh.mjs` corría `prisma migrate deploy --schema=prisma/schema.sqlite.prisma`
pero nunca regeneraba el cliente Prisma para ese schema. El cliente es singleton por
`node_modules/.prisma/client`: si el último `prisma generate` fue el default PostgreSQL
(p. ej. tras el job `unit-pg`, que corre `npx prisma generate` a secas), el seed de
`e2e:reseed-base` ejecutaba el client PG contra la base descartable SQLite y moría con
exit 1. Inferencial + refuter confirmado.

## ✨ Hitos Logrados

1. Nuevo paso (a.2) en `scripts/e2e-fresh.mjs`: `npx prisma generate
   --schema=prisma/schema.sqlite.prisma` con el `DATABASE_URL` propio de la base
   descartable, **entre** el `migrate deploy` y el `e2e:reseed-base`. Semántica del resto
   del script intacta (guardas `perf*.db`, jamás `dev.db`).
2. Encabezado del script actualizado: la lista de paridad con el job `e2e` del CI ahora
   declara 4 pasos (migrate → generate → seed → advertencias/comando).
3. Change openspec `e2e-fresh-prisma-generate` (proposal + design + tasks + delta
   `DEV-qa-lab` MODIFIED sobre "Corrida e2e única sin tag GATED (specs autónomos)" con el
   escenario "e2e:fresh fija el cliente Prisma SQLite antes del seed
   (R3-missing-prisma-generate)").
4. Nota en el runbook de operaciones (`docs/runbook-operaciones.md` §"Lane e2e local"):
   documenta el paso de generate y por qué existe. Evidencia RED→GREEN: con cliente PG,

   ("Lista: base fresca + seed completo").
