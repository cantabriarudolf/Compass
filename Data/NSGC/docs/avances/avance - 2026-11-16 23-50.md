# Avance — 2026-11-16 · cierre de F41 (el filtro de personal)

## Qué se corrigió

`/personas/personal` derivaba quién es personal con `p.datosLaborales !== undefined`. La API
manda `datosLaborales: null` (columna nullable de Prisma) para quien **no** tiene ficha, y
`null !== undefined` es `true`: el filtro metía al padrón entero. Consecuencias observables:

- el conteo de la pestaña «Trabajadores» incluía a todos los residentes activos;
- el selector de «Responsable interno» de los trabajos MT ofrecía a cualquier vecino;
- el cruce con tareas MT y el selector de turno trabajaban sobre esa lista inflada.

El criterio correcto ya estaba escrito en el servidor: `app/api/personas/route.ts` deriva el rol
`personal` con `datosLaborales != null`. La pantalla adopta el mismo, de modo que quien no tiene
ficha deja de existir como personal.

## Por qué se corrige recién ahora

Apareció midiendo el lote del techo de 100 del padrón (`odd/tasks/cerrar-el-techo-de-100.md`): al
cerrar el truncamiento de `personas/personal` se hizo evidente que el test sólo podía afirmar la
exclusión de quien no es personal si el fixture modelaba la ficha como clave ausente —el payload
que la API no manda—. Corregir el filtro era una línea, pero cambia a quién se le puede asignar
un trabajo, así que se abrió **F41** y se decidió con el owner antes de tocarla.
