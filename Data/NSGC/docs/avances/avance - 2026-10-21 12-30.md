## ✨ Hitos Logrados

### 1. H5 — el permiso vuelve al motor (`gd-guard` sin bypass)

| Antes | Ahora |
| --- | --- |
| `puedeGestionarActas` / `puedeGestionarControles` decidían con `if (rol === "comite") return true` | Una línea cada una: `return puede(rol, accion, "gd")` / `"ad"` |
| La matriz no declaraba `gd` para comité ni `ad` para nadie | `MATRIZ` declara `gd` y `ad` para comité (5 acciones) y `ad: ver` para residente |

Paridad exacta: ningún rol gana ni pierde acceso respecto del guard viejo. Test de paridad nuevo
(`test/api/gd-guard-paridad.test.ts`, 5 roles × 5 acciones) + `describe` en `lib/authz.test.ts`.

**Pregunta abierta al owner**: el comité conserva `eliminar` sobre actas y controles porque era lo que
el guard le daba. Recortarlo es una decisión de producto, no un efecto del refactor.

### 2. H7 — el destinatario marca la lectura, el admin no firma por otro

| Antes | Ahora |
| --- | --- |
| Solo `PUT /api/notificaciones/[id]` con `editar` (admin) | Nuevo `POST /api/notificaciones/[id]/leer` para el destinatario |
| El admin podía marcar leída una notificación ajena | El `PUT` del admin **descarta** `leida` si no es el destinatario |
| Sin permiso para el residente | Recurso granular `notificaciones:propias` (5 roles) |

Pertenencia validada server-side: notificación ajena → **404** (no 403, para no filtrar su existencia).
Idempotente. El mapa `rol → destinatarioRol` quedó con fuente única en `lib/api/notificaciones-scope.ts`.

**Deuda declarada**: `Notificacion` no tiene `fechaLectura`; el estado es solo `leida: Boolean`.
Agregar la fecha exige migración de esquema.

### 3. Un test que consagraba el defecto

`test/api/api-notificaciones.test.ts` tenía el caso "PUT marca como leída → 200 y refleja en BD", donde
el **admin** marcaba leída una notificación dirigida a un residente. Se reescribió al comportamiento
decidido en ambos sentidos: el destinatario la marca por el endpoint nuevo; el admin no puede cambiarla.
