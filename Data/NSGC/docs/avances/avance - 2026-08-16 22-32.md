# Avance de Desarrollo - 16 de Agosto de 2026

## 📋 Resumen: Convención de Capa de Datos ST en Módulos y Comando de Validación

Se ancló la convención de la capa de datos persistente (ST) en la documentación para que los módulos que aún no caen a OpenSpec (AD, AM, CF, CO, CT, CV, FI, GD, GE, IN, IR, MA, MT, PE, PI, PL, RA, RE, RP) lleguen con el contrato de datos claro y no repitan los errores históricos (imports estáticos de `data/`, `useState` de dominio, doble fuente de verdad). Se creó además un comando reutilizable de validación y se pushearon los commits pendientes.

## ✨ Hitos Logrados

1. **Regla de la casa en RG**: nueva regla en `RG - Reglas Generales.md` (sección 4, Consistencia de Datos): todo dato del dominio vive en `lib/store.ts` (Zustand + persist, `compass-store`); las páginas nunca importan entidades desde `data/` ni usan `useState` local para datos de dominio; mutación solo vía acciones CRUD del store (`saveX`/`removeX` con `StoreResult` y validaciones de integridad).
2. **Línea ST en 19 módulos pendientes**: cada spec de módulo sin OpenSpec ahora abre con `> 🔌 Datos: este módulo persiste en la capa de datos (ST) — ver ST - Capa de Datos Persistente.md`, haciendo cada documento autocontenido.
3. **Convención en el contrato OpenSpec**: `openspec/specs/project.md` declara la capa de datos como convención de desarrollo, para que el flujo `openspec-propose` la incorpore al generar changes (entidades + acciones en el store, seed desde mocks, integridad al eliminar).
4. **Comando `/valida-datos`**: `.opencode/commands/valida-datos.md` — validación de 5 puntos (artefactos OpenSpec, contrato de datos, antipatrones históricos, integración entre módulos, verificación tsc/lint) para pasarla a un módulo llevado a OpenSpec antes de darlo por cerrado.
5. **Push a origin/main**: 3 commits (`chore: remove openspec backup copy`, `feat: capa de datos persistente (ST) y pendientes de auditoría`, `docs: ancla convención de capa de datos ST en módulos y comando de validación`).
